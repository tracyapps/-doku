# Challenge service and Discord setup

The standalone Node/Express entry point is `server/index.ts`. Set PORT (default 3001). The Vercel catch-all adapter is `api/[...path].ts`. The web server must route `/api/*` to this service during development. No accounts or hosted resources are provisioned by this implementation.

Storage: without DATABASE_URL, a durable local JSON store is atomically replaced at `.data/challenges.json` (override with STARDOKU_DATA_FILE). Use one Node process with this local-file mode. With DATABASE_URL, PostgreSQL stores the data in `stardoku_store`; the table is created automatically and transactions use an advisory lock. A Neon connection string with its required SSL parameters is supported. Vercel requires DATABASE_URL: ephemeral function storage cannot provide durable results. The single JSON row is intentionally an initial implementation; migrate to normalized records before substantial traffic. Public challenges do not require an account. Bearer attempt credentials must remain private. Do not put tokens in share URLs.

Client helpers are exported from `src/game/network.ts`:

- `createChallenge(seed, variant)` returns `{id, seed, variant, results}`. Share `/?challenge=<id>` on your web origin.
- `getChallenge(id)` retrieves the puzzle family and posted results.
- `startChallengeAttempt(id, difficulty, name?)` returns `{attemptId, token, puzzle}`. Puzzle excludes the solution. Keep these credentials with the local attempt for resume.
- `submitChallengeResult(id, {attemptId, token, actions, elapsedSeconds})` returns a result. Submit all pen set/erase actions in order. Notes are private and omitted. Actions are `{kind:'set',cell,value}`, `{kind:'hint',cell}`, `{kind:'reveal',cell}`, `{kind:'check'}`, `{kind:'autofill'}`, `{kind:'autocheck',enabled}`, or `{kind:'conflicts',enabled}`. Values are 0–9, cells 0–80. Undo should replay a restoring set; prior first entries remain counted. Do not send actions that modify givens. Hints record guidance only; reveal actions fill the selected cell with the answer during server replay. Revealed cells are permanently excluded from first-entry accuracy, including any previous erroneous entry. Record toggles when enabled at the start as well as subsequent changes.

Result fields: id, name, difficulty, elapsedSeconds, accuracy (first nonzero pen entries correct / all first nonzero pen entries, rounded to a whole percent, or null when none), hints, checks, autofills, reveals, autocheck (ever enabled), conflicts (ever enabled), assisted (any recorded assistance), verification, completedAt. Results are idempotent per attempt. The server regenerates the puzzle, validates completion, and recomputes metrics from the submitted history. **History and elapsed time are self-reported.** Clients can fabricate events or derive solutions; this is friendly comparison, not an anti-cheat leaderboard. Display that label and keep dimensions separate, including difficulty. The server never returns solutions through challenge APIs, although the browser's local puzzle engine can derive them. Puzzle families with different difficulty use the same solution but different givens.

Discord: application `1548073007950602303` is the configured public client ID. `initializeDiscord()` resolves with `{status:'browser'|'unavailable'|'connected', message, username?}` without blocking solo play. The client ID has an in-code public fallback and remains configurable through VITE_DISCORD_CLIENT_ID; set server-only DISCORD_CLIENT_ID and DISCORD_CLIENT_SECRET for token exchange. Configure the Discord Activity URL mapping to the deployed origin and route API calls on that origin. The SDK currently authorizes the identify scope; `/api/discord/token` exchanges the one-time code on the server. Tokens stay in memory. There is no authenticated association of challenge names/results with Discord accounts yet. Discord Activity hosting, Developer Portal configuration and real in-Discord verification remain deployment work.

Launch scope: keep the default Discord-managed Entry Point handler for the initial Activity release. It opens the Activity and posts Discord's standard launch message. Completed-result sharing remains an explicit user action. Prefer Discord's native share-link or share-moment dialog for the first release; this lets the user choose a server channel, DM, or group DM without giving the app permission to enumerate or read channels.

Live group cards are a separate guild-bot phase. Store `guildId`, `channelId`, `messageId`, and `challengeId` when the bot creates the card, then edit that known message when a result arrives. The minimum proposed channel permissions are View Channel, Send Messages, Embed Links, and Attach Files. Do not request Read Message History merely to rediscover the bot's own card. Server administrators can restrict those permissions to chosen game channels.

Operational limits: JSON body limit 256 KB, 10,000 actions, 40-character names, 100-character seeds, and a basic per-process request rate limit. This rate limit is not global in serverless deployments. There is no automatic record retention policy yet. Add identity, shared rate limiting, normalized persistence and a retention policy before broad public promotion.
